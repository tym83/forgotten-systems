# Находка 46. Переключить тег каталога недостаточно

Каталог подключается к Cozystack ссылкой на OCI-артефакт. Кажется, что для
обновления хватит переставить тег у `OCIRepository` — платformа подтянет новую
ревизию и всё разложит.

Не хватит. **Список компонентов живёт в манифесте `PackageSource` внутри
кластера** и вместе с артефактом не обновляется.

## Как это выглядит

Артефакт обновился, ревизия новая, состояние зелёное:

```
ревизия: v0.1.5@sha256:b26e78...
Ready=True Succeeded: reconciliation succeeded, generated 4 artifact(s)
```

Четыре — а компонентов в новой версии пять. Новое приложение видно в каталоге
(описания раскладывает отдельный компонент, и он-то обновился), тенант его
ставит — и оно не разворачивается:

```
could not get Source object: ExternalArtifact ... not found
```

## Почему так

Состояние размазано по двум местам:

| где | что | обновляется |
|---|---|---|
| `OCIRepository` | ссылка и ревизия | сменой тега |
| `PackageSource` | **список компонентов** | только повторным `tap` |

Первое меняется одной командой, второе — нет, и ничто об этом не сообщает.

## Что делать

Обновлять каталог повторным подключением, а не правкой тега:

```
cozypkg tap oci://ghcr.io/<владелец>/<репозиторий>:<новая-версия>
```

После него источник перечитывает список:

```
reconciliation succeeded, generated 5 artifact(s)
```

## Общее с остальными ловушками каталога

Тот же почерк, что в находках 35 и 45: **всё зелёное, и ничего не работает**.
Состояние разложено по нескольким местам, обновляется частично, а проверка
смотрит на то, что обновилось.

Практическое правило: после обновления каталога сверять не состояние источника,
а **число порождённых артефактов** с числом компонентов.
